## 🎯 1. Цели и назначение (Overview & Goals)

### Контекст проблемы
В текущей рабочей версии рендеринг видеоконтента (Remotion Chromium Headless, видеокодирование через FFmpeg и пост-обработка Uniquifier) по умолчанию выполняется на CPU с кодеком `libx264` и программной растеризацией WebGL/CSS.
- На современных машинах с дискретными или мощными интегрированными видеокартами (AMD Radeon 780M / RDNA3, NVIDIA RTX / NVENC, Intel Iris Xe / QSV) процессор перегружен на 100%, а рендеринг 60-секундного 60fps ролика занимает 60–120 секунд.
- При повторных генерациях Remotion пересобирает Webpack-бандл с нуля, тратя лишние 8–15 секунд на каждый ролик.
- Пост-обработка в `uniquifier.py` принудительно перекодирует видео на CPU через `libx264`, добавляя еще 15–25 секунд ожидания.

### Цель фичи
Внедрить двухуровневый профиль рендеринга:
1. **`gpu_fast` (Аппаратное GPU-ускорение)**:
   - Автоматическое определение GPU и аппаратного кодека (AMD AMF `h264_amf`, NVIDIA NVENC `h264_nvenc`, Intel QSV `h264_qsv`, либо Windows MediaFoundation `h264_mf`).
   - Включение аппаратного ANGLE/DirectX GPU-рендеринга для Chromium в Remotion (`--gl=angle`).
   - Кэширование Webpack-сборки (`--bundle-cache`) для исключения накладных расходов при повторных рендерах.
   - Аппаратное кодирование в `remotion.config.ts` через `Config.overrideFfmpegCommand`.
   - Аппаратное кодирование в `uniquifier.py` (ускорение с 20с до 1.5с).
2. **`cpu_safe` (Программная надежность)**:
   - Стандартный режим на базе CPU и `libx264` для машин без совместимых видеокарт или виртуальных машин.
3. **Удобный переключатель в веб-интерфейсе**:
   - Интуитивный выбор режима в карточке генерации на странице `quiz.html`.
   - Автоматический опрос возможностей оборудования (`/api/v1/hardware/status`) с отображением бейджа обнаруженной видеокарты (например, `🟢 GPU: AMD Radeon 780M (AMF/Direct3D)`).
   - Сохранение пользовательского выбора в `localStorage`.

## Clarifications

### Session 2026-10-12
- Q: Как система должна реагировать, если при активном режиме `gpu_fast` рендеринг через GPU завершается ошибкой (например, сбой видеодрайвера, нехватка видеопамяти VRAM или сбой инициализации ANGLE)? → A: Автоматический бесшовный перезапуск в `cpu_safe` (`libx264`) с записью предупреждения в лог, гарантирующий 100% успешное получение видео пользователем.
- Q: Как должен вести себя веб-интерфейс, если система запущена на компьютере или сервере без поддерживаемого GPU (`gpu_available: false`)? → A: Кнопка `[⚡ GPU Fast]` визуально блокируется (`disabled`) с бейджем "GPU не обнаружен (активен CPU Safe)".
- Q: Какой приоритет аппаратных энкодеров должна использовать система при наличии нескольких видеокарт? → A: Каскадный авто-приоритет: Дискретный GPU (NVIDIA `h264_nvenc`) > Интегрированный GPU (AMD `h264_amf` / Intel `h264_qsv`) > Windows MediaFoundation (`h264_mf`) > CPU (`libx264`).
- Q: Какой профиль качества и битрейта должен использовать аппаратный энкодер в режиме `gpu_fast`? → A: Высокое качество (10–12 Мбит/с High Quality) для идеальной резкости текста и анимаций без блочности.
- Q: Как система должна управлять кэшем сборки Webpack Remotion (`--bundle-cache`) между перезапусками приложения? → A: Постоянный кэш (Persistent Cache), сохраняющийся между сессиями для мгновенного старта каждого рендеринга.

## 👥 2. Пользовательские сценарии и тестирование (User Stories)

### User Story 1 — Переключение режима и ускоренный рендеринг через GPU (Приоритет: P1)
**Как** контент-мейкер, генерирующий Shorts-квизы через веб-интерфейс,  
**Я хочу** иметь возможность в один клик включить режим "⚡ GPU Fast" с аппаратным упором в мою видеокарту,  
**Чтобы** генерация и рендеринг роликов происходили в 3–5 раз быстрее без 100% блокировки процессора.

#### Критерии приемки (Acceptance Criteria):
1. **Given** открыт веб-интерфейс `quiz.html`,  
   **When** страница загружается,  
   **Then** система опрашивает `/api/v1/hardware/status`, отображает статус видеокарты и активирует режим `⚡ GPU Fast` по умолчанию (или сохраненный из `localStorage`).
2. **Given** выбран профиль `gpu_fast`,  
   **When** пользователь нажимает "Создать видео",  
   **Then** в API отправляется `render_profile: "gpu_fast"`, Remotion запускается с параметрами `--gl=angle --bundle-cache`, а FFmpeg кодирует видео через аппаратный энкодер (`h264_amf` / `h264_nvenc` / `h264_qsv` / `h264_mf`).
3. **Given** завершен рендер Remotion,  
   **When** запускается финальный уникализатор видео `uniquifier.py`,  
   **Then** он использует аппаратный энкодер, завершая обработку за 1–3 секунды вместо 15–25 секунд.

---

### User Story 2 — Надежный Fallback и переключение в CPU Safe (Приоритет: P2)
**Как** пользователь системы, работающий на сервере без GPU или столкнувшийся с редким сбоем видеодрайвера,  
**Я хочу** иметь возможность переключиться в режим "🖥️ CPU Safe" (или чтобы система сделала это автоматически при ошибке GPU),  
**Чтобы** генерация гарантированно завершилась успешно в 100% случаев.

#### Критерии приемки:
1. **Given** пользователь вручную выбрал "🖥️ CPU Safe",  
   **When** запускается генерация,  
   **Then** оркестратор и медиа-пайплайн используют проверенный `libx264` без GPU-флагов.
2. **Given** выбран режим `gpu_fast`, но видеодрайвер выдал временную ошибку инициализации,  
   **When** пайплайн перехватывает ошибку аппаратного энкодера,  
   **Then** он автоматически перезапускает рендер в режиме `cpu_safe` с предупреждением в логах, предотвращая падение задачи.

---

### User Story 3 — Полная сквозная оптимизация пайплайна (Приоритет: P3)
**Как** пользователь, создающий множество квизов подряд,  
**Я хочу**, чтобы все вспомогательные этапы (аудио, изображения, Webpack бандлинг) были максимально оптимизированы,  
**Чтобы** суммарное время ожидания от нажатия кнопки до готового MP4 сократилось до минимума.

#### Критерии приемки:
1. **Given** повторный запуск рендеринга Remotion с неизменными исходниками шаблона,  
   **When** Remotion стартует с `--bundle-cache`,  
   **Then** фаза бандлинга занимает менее 1 секунды (против 8–15 секунд без кэша).
2. **Given** генерация аудиодорожек и картинок,  
   **When** оркестратор готовит медиа-ресурсы,  
   **Then** запросы на скачивание и генерацию выполняются асинхронно и параллельно без лишних задержек.

## 🔒 3. Нефункциональные требования (Non-Functional Requirements)

1. **Совместимость с оборудованием**:
   - AMD (Radeon 600M/700M/800M, RX 5000/6000/7000/8000 через `h264_amf`).
   - NVIDIA (GeForce GTX/RTX через `h264_nvenc`).
   - Intel (Arc, Iris Xe, UHD через `h264_qsv`).
   - Windows Generic (любая видеокарта с поддержкой Direct3D 11/12 через `h264_mf`).
   - Linux / macOS (поддержка `vaapi` / `videotoolbox` с прозрачным фолбэком на `libx264`).
2. **Качество видео**:
   - При аппаратном кодировании визуальное качество обязано быть неотличимо от `crf 18` (битрейт 8–12 Мбит/с с CBR/VBR и качеством High).
3. **Безопасность и стабильность**:
   - Никаких крешей процесса при недоступности GPU.
   - 100% прохождение всех существующих 65 юнит-тестов и linter checks.
